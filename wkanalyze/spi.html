How WebKit’s audit-spi Enforces Private API Usage

Created on March 11, 2025 (0a497503904f), populated with initial allowlists on July 9, 2025 (cbb5741c87c7), and enforced on iOS builds on September 4, 2025 (2483129e9349), audit-spi (Tools/Scripts/libraries/webkitapipy) runs at build time against compiled WebKit Mach-O binaries:

  • Public Baseline (SDKDB): Reads 135 TAPI-generated WebKitLibraries/SDKDBs/iphoneos/*.partial.sdkdb files (indexing 130,849 public symbols, 3,375 public ObjC classes, and 12,183 public ObjC selectors).
  • Binary & Soft-Link Inspection: Scans Mach-O imported symbol tables, __objc_selrefs, and WebKit’s dedicated __TEXT,__dlsym_cstr and __TEXT,__getClass_cstr sections emitted by SOFT_LINK* macros (Source/WTF/wtf/cocoa/SoftLinking.h).
  • Allowlist Gate: Any symbol, class, selector, or Swift declaration absent from the public SDKDB fails the build unless allowlisted in AllowedSPI.toml or AllowedSPI-legacy.toml.

3P Availability Tiers for Alternative Browser Engines

  • Tier 1: Restricted Entitlement / XPC Daemon (375 SPIs / 18.6%) Gated at runtime by restricted com.apple.private.* or system entitlements or privileged Mach services inaccessible to 3P apps and 3P browser engines.
  • Tier 2: Internal SDK Only (260 SPIs / 12.9%) Gated by requires = ["USE_APPLE_INTERNAL_SDK"], categorized as [[not-web-essential]], or bound to internal-only private frameworks.
  • Tier 3: BrowserEngineKit / System WebKit (847 SPIs / 42.1%) Raw SPI symbols are private, but equivalent capabilities are exposed to approved 3P EU browser engines via BrowserEngineKit or to standard apps via WKWebView.
  • Tier 4: In-Process Private Symbol (501 SPIs / 24.9%) In-process private C/ObjC symbols in public frameworks that do not check a Mach entitlement at runtime, but are undocumented and prohibited by App Store review.
  • Tier 5: Conditionally Promoted (31 SPIs / 1.5%) Guarded by !SDKDB_HAS_* or requires-sdk after promotion to public API in newer iOS SDKs.

Executive Briefing • Architecture & Interoperability Context

What Are iOS Private APIs (SPIs) & Why Does WebKit Track Them Under the EU Digital Markets Act?

On iOS, Apple separates operating system interfaces into two tiers: documented Public APIs (shipped in the public Xcode SDK for all App Store developers) and undocumented System Programming Interfaces (SPIs) reserved for Apple’s own system frameworks and first-party apps. Understanding how WebKit relies on 2,014 unique iOS SPIs—and how WebKit audits them—is central to evaluating browser engine competition and interoperability under the EU Digital Markets Act (DMA).

1 Public SDK APIs vs. Private iOS SPIs

Overview: When third-party developers build iOS apps, they are contractually and technically restricted to Apple’s Public SDK. However, iOS frameworks (like UIKit, CoreText, AVFoundation, Network, and Security) also expose thousands of internal hooks—called SPIs—that provide lower-level hardware control, direct kernel/daemon IPC, and privileged system UI integration.

Technical Enforcement Mechanism: WebKit accesses SPIs through private headers (*SPI.h) and runtime dynamic linking macros (SOFT_LINK*) that embed symbol names into custom Mach-O binary sections (__TEXT,__dlsym_cstr and __TEXT,__getClass_cstr). WebKit’s build-time scanner audit-spi (webkitapipy) compares every symbol, class, Objective-C selector, and Swift declaration referenced by compiled WebKit binaries against 135 public iOS SDK databases (*.partial.sdkdb).

GitHub: cbb5741c87c7

2 Why DMA Articles 6(4) & 6(7) Drive SPI Auditing

Regulatory Context: For 16 years, Apple required all iOS web browsers to use Apple’s own WKWebView / WebKit rendering engine. Under the EU Digital Markets Act—specifically Article 6(4) (enabling alternative browser engines) and Article 6(7) (requiring gatekeepers to provide third parties, free of charge, “effective interoperability with, and access for the purposes of interoperability to, the same hardware and software features” available to the gatekeeper’s own services)—Apple introduced BrowserEngineKit in iOS 17.4+.

The Architectural Asymmetry: Because WebKit is built as a first-party system framework, it directly invokes 2,014 private iOS SPIs across 66 OS frameworks. While 847 SPIs (42.1%) have functional equivalents bridged through BrowserEngineKit or system WebKit, 635 SPIs (31.5%) are strictly Apple-only (375 blocked by private entitlements/daemons + 260 gated by USE_APPLE_INTERNAL_SDK), and another 501 SPIs (24.9%) are undocumented in-process private symbols prohibited by App Store review.

3 Two-Tier Allowlists & The “Legacy” Freeze Paradox

How WebKit Tracks SPI Debt: WebKit splits its private API allowlists across 5 modules (JavaScriptCore, WebCore, WebGPU, WebKit, WebKitLegacy) into two distinct TOML files per module:

  • AllowedSPI.toml (198 raw / 197 unique entries at HEAD): The modern reviewed allowlist. Entries must declare a structured reason (temporary-usage, not-web-essential, staging, or equivalent-api) and bug links (request / cleanup).
  • AllowedSPI-legacy.toml (1,899 raw / 1,889 file-unique entries at HEAD): The grandfathered technical-debt list, headed by the explicit rule: # NEVER add to this list, only remove!

Empirical Finding: Because no script enforces non-growth on AllowedSPI-legacy.toml, 24 post-baseline commits added +215 gross entries (191 net-new + 24 re-added), leaving 133 net-new post-baseline entries (+18 re-added = 151) in AllowedSPI-legacy.toml at HEAD without request/cleanup tracking.

Governance & Policy Audit Spotlight

Additions to the “Legacy” Allowed SPI List (AllowedSPI-legacy.toml) Which Isn’t Supposed to Grow

Audit of all five AllowedSPI-legacy.toml files comparing their initial July 9, 2025 baseline (cbb5741c87c7, 1,956 entries) against every subsequent commit through September 30, 2026 (a216b77387a6, 1,889 entries).

# NEVER add to this list, only remove!
Every AllowedSPI-legacy.toml file in JavaScriptCore, WebCore, WebGPU, WebKit, and WebKitLegacy begins with this explicit directive. However, neither webkitapipy/allow.py nor Tools/Scripts/webkitpy/style/checkers/spi_allowlist.py enforces a non-growth check on legacy lists, and [[legacy]] blocks require no request (radar requesting a public SDK replacement) or cleanup bug URLs. As a result, adding entries to AllowedSPI-legacy.toml bypasses WebKit’s formal public-API replacement workflow.
